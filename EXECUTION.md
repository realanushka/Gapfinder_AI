- ✅ `migrations/env.py` wired to `app.database.Base` + `app.models`, reads `DATABASE_URL` from `.env` (so the connection string is never duplicated in `alembic.ini` or committed). Includes an `include_object` filter restricting autogenerate to our own tables, so it can never emit `DROP` for Supabase-owned objects in `public`

- ✅ Initial revision hand-written at `migrations/versions/0001_initial_schema.py` — self-contained (enum labels and embedding dim inlined, no app imports) so it stays a frozen snapshot. Creates the `vector` extension *before* the `chunks.embedding` column, then all 10 tables in FK-safe order
- ✅ Added an **HNSW index** (`ix_chunks_embedding_hnsw`, `vector_cosine_ops`) on `chunks.embedding`, declared on the model so autogenerate won't later drop it. Without this every retrieval query sequential-scans all chunks
- ✅ Fixed an enum-label bug found during setup: SQLAlchemy defaults to storing enum *member names* (`SYLLABUS`, `WEAK`), but [ARCHITECTURE.md §3](./ARCHITECTURE.md#3-database-schema), the Pydantic layer and `planning_service.MINUTES_BY_STATUS` all use lowercase *values*. Both enums now use `values_callable` so Postgres stores `syllabus`/`weak`
- ✅ Verified offline: `alembic upgrade head --sql` produces valid SQL, the downgrade path reverses cleanly (including dropping enum types), and a metadata-vs-migration diff confirms **all 10 tables / 54 columns match the models exactly**
- ✅ `backend/scripts/verify_db.py` written to introspect the live DB (extension, tables, HNSW index + opclass, enum labels, stamped revision)

Notes on decisions made while building:

- **`cacheComponents` and `partialPrefetching` are both disabled** in `next.config.ts` (both were create-next-app defaults). Protected pages are gated by a client-side auth check, so their segments render nothing until the session resolves, and Next's instant-navigation validation logged an error for every protected route on every request. The documented per-segment opt-out (`export const instant = false`) can't be used because it requires a Server Component and these pages are all `"use client"`. Turning off `partialPrefetching` alone did **not** silence it — `cacheComponents` drives that validation. Neither flag buys anything here, since every page is a client component fetching from the API at runtime and nothing uses `use cache`.
- **Three `setState`-in-effect lint errors were fixed by deriving rather than mirroring state.** The Quiz and Explain pages previously copied `?topic=` into state via an effect; they now derive it and stamp any user edit with the URL value it was made under, so following a new "Revise this" link resets the form with no synchronisation code.
- **Two backend gaps were closed to make the UI work**, see Phases 3 and 5 below.

## Phase 4 — Topic map (Plan Step 4)

`POST /topics/build-from-syllabus/{document_id}` now runs the **whole Step 4 pipeline** in one call, because the steps are order-dependent (linking needs topics; exam weights need mapped past questions):

- ✅ Syllabus text is reassembled from the document's chunks — this was a placeholder empty string, so extraction previously returned nothing
- ✅ LLM extracts the topic tree as strict JSON; parent/child `Topic` rows persisted
- ✅ **Topic ↔ chunk linking**: each topic name is embedded and vector-searched against the user's notes/textbook chunks, writing `chunk_topics`. Without this `chunk_topics` stayed empty and `/quiz/generate` always 404'd — the quiz could not run at all
- ✅ **Past-paper mapping**: papers split into questions by regex (`Q1.` / `Q2)` / `3.` / `12.` — all four styles verified), each embedded, shortlisted by similarity, then confirmed by the LLM; saved to `past_questions` with the year parsed from the filename
- ✅ **Exam weight** recomputed as the count of past questions per topic
- ✅ Rebuilds are **safe and idempotent**: topics are upserted by name rather than deleted, because `questions` and `topic_scores` both cascade from `topics` — deleting would have silently destroyed quiz history. Chunk links and a paper's own past questions are cleared before rewriting, so re-running cannot double-count exam weights
- ✅ Migration **0002** adds `past_questions.document_id`: `topic_id` is nullable so it cannot identify the owning user, and re-mapping needed a way to clear its own prior rows
- ✅ Frontend: Topic Map page — syllabus picker, nested tree with exam-frequency badges, "Quiz me" per topic, and a result line reporting topics extracted / chunks linked / past questions mapped

## Robustness of the AI calls

Retries are implemented in `app/services/retry_policy.py`, in two deliberately separate layers:

- ✅ **Transport failures** (connection errors, 408/409/429, 5xx) are retried by the SDKs themselves. Both clients now set `max_retries=3` and an explicit `timeout` rather than relying on the invisible default of 2 — wrapping these again in application code would only multiply the attempt count.
- ✅ **Unusable 200 responses**, which the SDKs cannot retry because the HTTP call succeeded, are handled by `retry_on_bad_response`: unparseable JSON, a JSON array where an object was expected, or embeddings of the wrong width/count. Three attempts, exponential backoff with jitter.
- ✅ **Permanent failures fail fast** on the first attempt: auth errors, other 4xx, safety refusals, and output truncation (the same prompt against the same ceiling truncates again, so retrying would triple the cost to reach the same failure).

Three latent bugs in `llm_client.py` were found and fixed while doing this — retries would have masked them rather than helped:

- ✅ **`response.content[0].text` assumed the first block is text.** Thinking is on by default on current models and the raw chain of thought is never returned, so the first block is typically a thinking block with empty text — the call returned `""`, then failed JSON parsing. Now concatenates all `type == "text"` blocks.
- ✅ **`max_tokens` caps thinking *and* visible output together.** At 2048 the JSON was liable to truncate mid-object, surfacing as a parse error rather than an obvious size failure. Raised to 8192 for JSON, and `stop_reason == "max_tokens"` is now detected explicitly.
- ✅ **`stop_reason` was never checked**, so a safety refusal looked like an empty response. Refusals now raise `LLMRefused` immediately.

Also added: markdown code-fence stripping (models wrap JSON in ```json fences even when told not to, which caused avoidable retries) and embedding shape validation before the vectors reach Postgres (a wrong width otherwise fails on insert with an opaque pgvector dimension error far from the cause, and a short batch would silently mis-pair chunks with embeddings via `zip()`).

Verified by test rather than assumption: recovers on retry (2 calls), exhausts at exactly 3, re-raises the original exception rather than leaking tenacity's `RetryError`, and makes exactly **1** call for truncation and for refusal. All new exceptions subclass `RuntimeError`, so existing callers keep working.

Remaining gap: the prompts still *ask* for JSON rather than guaranteeing it. **Structured outputs** (`output_config.format` with a JSON schema) would make malformed JSON impossible instead of retried — the stronger fix, needing one schema per call site.

## Suggested order of attack

Backend and frontend are both built and verified in isolation. Nothing has run end-to-end yet, because that needs the database. All the application code is written; what remains needs credentials or a human:

1. **Unblock the database** (Phase 1) — put the Supabase connection string in `backend/.env`, then:
   ```bash
   cd backend
   venv/Scripts/python.exe -m alembic upgrade head
   venv/Scripts/python.exe -m scripts.verify_db
   venv/Scripts/python.exe -m scripts.seed_demo
   ```
2. **Add API keys** to `backend/.env` (`OPENAI_API_KEY` for embeddings, `ANTHROPIC_API_KEY` for generation). Uploading new material and every LLM step need them; the seeded demo account does not.
3. **Walk the demo flow for real** with both servers running, and fix what surfaces. Nothing has executed against a live database yet — every check so far has been static (imports, typecheck, lint, build, offline SQL, route status codes).
4. **Deploy** (Vercel + Render/Railway) and rehearse.
